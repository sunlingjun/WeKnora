## 0. 范围

**做：** 以工作空间（`tenants.id`）为边界，把本空间**自己拥有的**知识库 / 知识 / 工作空间成员变化，推到 Owner 配置的 HTTPS 回调。

**不做（本 PR）：** 农信 CAS、天工专用字段、`open_retrieve`、change feed、**组织共享扇出**、`kb.share_*`、Agent 分享可见库、广场 `knowledge_base_members`。

**和目录拉取的分工**（见 `docs/feature/2026-08-31-工作空间授权知识目录拉取设计.md`）：

| | Webhook（本文） | Catalog |
|--|----------------|---------|
| 作用 | 归属空间的**增量**推送 | 空间 Key 拉「自有 ∪ 组织分享」**全量底** |
| 组织分享库 | P0 **没有**事件 | 靠目录建底 + `updated_after` 轮询（删除仍可能漏） |
| 源文件 | 回调里的 5 分钟票 → `/files/knowledge-download/:id` | 现网 `GET /knowledge/:id/download`（Viewer / 分享 viewer **不能**下） |

现网没有第二套「空间级知识生命周期出站 Webhook」。Embed 是聊天出站且不重试；IM 是入站；审计是人拉。本模块独立，只复用 SSRF 客户端与 `SystemHMACKey()`。

**成功标准：** 上传立刻 `knowledge.created`（可带票，不可当已检索）；worker 里 `parse_completed`（可早于 created）；单条删 / 批量删 / 解析失败有事件；建库删库有事件且删库不刷 N 条文档事件；工作空间成员进出有事件；多回调、HMAC、SSRF；失败不回滚业务；outbox 至少一次。

## 1. 架构

```text
  用户 / API / 数据源 / asynq worker
           │  业务状态写成功
           ▼
  WorkspaceEventSink.Emit
           │  同库 INSERT outbox（失败重试 3 次，仍不回滚业务）
           ▼
  Dispatcher（同进程试一次 + 每 10s sweep pending）
           │  只查 归属空间 的 tenant_webhook_endpoints
           │  enabled 且 events 显式包含该 type
           │  INSERT delivery 认领 (event_id, endpoint_id)
           │  asynq.Enqueue TaskID=wh:{event_id}:{endpoint_id}
           ▼
  QueueWebhook + WorkerPoolWebhook（第 7 个 asynq Server）
           │  in-flight < 20 才 POST，否则 ErrWebhookInFlightBusy
           │  现签下载票 → Timestamp HMAC → HTTPS POST
           ▼
  用户配置的接收端（每空间最多 5 个 URL）
```

**三条原则：**

1. 业务写入不同步 HTTP。Emit = 写 outbox。
2. 没有 outbox 行不许声称 at-least-once。asynq 只是投递器。接收方按包络 `id` 去重（不是 exactly-once）。
3. 审计给人看，webhook 给机器。

**为何不是别的：**

| 不采用 | 原因（现网） |
|--------|----------------|
| Gin 拦截 | `parse_completed` 发生在 worker：`finalizeIndexedKnowledgeState`、post-process 无子任务、`FinalizeSubtask` 且 `promoted==true`。HTTP 中间件会漏完成态。 |
| RAG `EventBus` | 每请求一份、服务问答 SSE，同步出错会中断问答。 |
| `tenants` JSONB / KV | 多端点、密钥、过滤、投递日志需要独立表；密钥不能出现在 `GET /tenants/:id`。 |
| 包装整个 `KnowledgeRepository` | 30+ 方法，后续每次加方法都要转调。 |
| 挂 `QueueMaintenance`（Redis 名 `"low"`） | 与删库/clone 同池；HTTP 10s×重试会拖维护任务。 |
| 内存 Bus 当真源 | HTTP 与 worker 跨进程。真源是 outbox + sweep。 |
| 复用 Embed HMAC | Embed 只签 body、不重试。工作空间签 `timestamp + "." + raw_body`。禁止合成一个函数。 |
| 旁路现网 `GET /knowledge/:id/download` | 该路由 Contributor+ 且 `KBAccessWrite`；把 `/api/v1/knowledge/` 加白名单会放开整个知识 API。 |

## 2. 确定决策（合并历次审查，无矛盾）

### 2.1 投递范围

只投 **资源所属工作空间** 的端点。包络 `tenant_id` = 知识/库行 `tenant_id` = 票内 `tenant_id`。P0 不扇出到组织成员，因此不存在「票 401」和「扇出带票绕过 Viewer 下载 ACL」。

`data.owner_tenant_id` 仍保留，P0 与包络 `tenant_id` 相同（给 P1 扇出留字段）。签发/校验票 **始终读知识行 `TenantID`**，即使以后扇出也不改。

组织分享、入组补 `share_*`、删库通知成员、Agent 分享：**P1**。成员空间增量靠 Catalog，不靠本 PR。

### 2.2 可靠性

| 问题 | 确定做法 |
|------|----------|
| 丢失 | 先 outbox 再入队。仅 INSERT outbox 失败（库挂）才丢，打 `webhook_outbox_insert_failed`。 |
| in-flight 满（每空间同时 POST≤20） | `return ErrWebhookInFlightBusy`。**禁止** `SkipRetry`（会归档，而 outbox 已 `processed`）。webhook Server：`IsFailure=false` 不耗 MaxRetry；`RetryDelayFunc` 固定 3s。`delivery_id` 入队时生成，重试不变。没 POST 不加 `attempts`。槽位 INCR，满则 DECR 后返回 busy；占到才 POST，`defer DECR`。 |
| 部分入队双投 | ① `asynq.TaskID("wh:"+event_id+":"+endpoint_id)`，`ErrTaskIDConflict` 当已入队。② deliveries **UNIQUE(event_id, endpoint_id)** 持久认领；已 `success`/`failed` 不再入。全部端点认领并入队后才把 outbox 标 `processed`。只靠 TaskID 不够：成功后 asynq 释放 ID，崩溃在 `UPDATE processed` 前会再投。 |
| HTTP 重试 | 2xx 成功；408/429/5xx 指数退避，MaxRetry=5；其它 4xx（除上述）`SkipRetry` 标 failed。 |
| Lite 无 Redis | 仍写 outbox；同进程同步 POST；进程内 in-flight。不声称跨进程 at-least-once。 |

### 2.3 事件语义（对齐现网写入点）

| 项 | 确定做法 |
|----|----------|
| `parse_completed` | `parse_status` **从非 completed 转入 completed**（含重解析）。不是「用户启用」。现网无停用文档 API；`enable_status` 是流水线字段。已 completed 再 Update 其它列 **不发**。`FinalizeSubtask` 只在 `promoted==true`。 |
| 删除 | 软删成功后发。`DeleteKnowledge` → `knowledge.deleted`；`DeleteKnowledgeList` `len==1` → deleted，`len>1` → **只** `batch_deleted`。HTTP enqueue **不发**。`ProcessKBDelete` 走仓储 `kgRepo.DeleteKnowledgeList`，**禁止**改成 service（否则会刷 N 条文档事件）。 |
| 删库 | 一条 `kb.deleted` + `cascade_knowledge: true`，只投拥有空间。无 `data.download`。 |
| `kb.created` | 凡 service 层 `repo.CreateKnowledgeBase` 成功且 `!IsTemporary`：`CreateKnowledgeBase`、`DuplicateKnowledgeBase`、`CopyKnowledgeBase`（`dstKB==""` 新建）、slj `CreateSharedKnowledgeBase`。拷进已有库不发。 |
| `knowledge.created` | `repo.CreateKnowledge` 成功之后。入口：FromFile / URL / Manual / Passage / `cloneKnowledge`。FAQ 容器壳不发。临时库跳过。 |
| 同 ID 换库 | `moveKnowledgeReparse`：deleted（旧库 id）+ created（新库 id）。接收方用 `knowledge_base_id` 判断，不得用迟到的 deleted 清掉已在新库的行。 |
| 成员 | `tenant_members` 新插入 → `rbac.member_added`；Remove/Leave → `rbac.member_removed`（`reason=left`）。**禁止** `EnsureOwner`。孤儿空间自愈走 `AddMember`，会发（极少，接受）。 |
| 乱序 | P0 允许。completed 可早于 created。去重键是包络 `id`。 |
| `batch_deleted` 截断 | ids 最多 100。`truncated=true` **不能**靠 `ListKnowledge` 找回已删 id（列表不含软删行）。对端应分页拉该库**仍存在**的知识，本地同库且不在列表中的摘掉。 |

### 2.4 契约与安全

| 项 | 确定做法 |
|----|----------|
| 字段名 | `knowledge_type`=`file\|url\|manual\|faq`；KB `visibility` 仅 `private\|shared`；根目录 `folder_path=""`。 |
| 包络 | 字段集合固定，不缺 key。只按顶层 `type` 分支。 |
| `events` | 禁止空数组。未订阅的未来 type 不投。测试按钮绕过过滤。 |
| CRUD | `/api/v1/tenants/:id/event/webhooks`，挂 `tenantByID` + `PathTenantMatch`。JWT `g.Owner()`。API Key 必须 `apiKeyRoute` + `manage_tenant_settings`（未声明的 `/tenants/:id/*` 默认拒绝）。 |
| HMAC | `SignWebhookTimestampBody`；Header `X-WeKnora-Timestamp` + `X-WeKnora-Signature: sha256=`。Embed 保持只签 body。`User-Agent: WeKnora-Workspace-Webhook/1.0`。 |
| 票 | 5 分钟；POST 前现签；绑 `purpose + knowledge_id + 知识行 TenantID + exp`；共用 `SystemHMACKey()`。独立面 `GET\|HEAD /api/v1/files/knowledge-download/:id`。`noAuthAPI` methods **含 POST**（renew）。换票 grace 默认 1 小时，泄露窗按此写。IP 限流。不改现网 download。 |
| 队列 | `WorkerPoolWebhook` / `QueueWebhook="webhook"` / `SharedWeight=0`。第 7 个 Server。**不要**并进 `DefaultUpstreamWorkerConcurrency`。必须改 `validPools`、`WorkerPoolConcurrency.Webhook`、container、`RunAsynqServer.runPool`、`GetRuntimeQueues`、`system_runtime_test`。 |
| 迁移 | PG `000080`（合入前若上游已占用则顺延）+ sqlite `000003`。DDL 用 `COMMENT ON COLUMN`，不要 MySQL 列级 `COMMENT`。 |
| i18n | zh-CN / en-US / ko-KR / ru-RU 同一 key。 |

## 3. 事件目录

事件名与现有 `AuditAction` 的 dot-namespace 对齐。接收方 **只按顶层 `type` 字符串分支**。

### 3.1 P0（本模块必须发出）

| `type` | 何时发出 | 接收方典型动作 |
|--------|----------|----------------|
| `knowledge.created` | 文件 / URL / 手工知识行插入成功 | 建目录占位；可按 `data.download` 拉源文件；**不可检索** |
| `knowledge.parse_completed` | 索引流水线把 `parse_status` **从非 completed 转入** `completed`（含重解析完成）。现网完成时会把 `enable_status` 设为 `enabled`。**不是**「用户点了启用」——现网没有该入口 | 按 `enable_status` 决定是否可检索；未知 id 则先 upsert 再等可能迟到的 `created` |
| `knowledge.parse_failed` | 变为 `failed`（含重解析失败） | 标红、告警 |
| `knowledge.deleted` | **单条知识行**软删成功（见 §10.1 清单，含 `DeleteKnowledge`） | 按 `knowledge_id` 从目录摘掉 |
| `knowledge.batch_deleted` | **一次调用删多行**成功（`DeleteKnowledgeList` 且 `len>1`）。**不是** HTTP enqueue 成功 | 按 `knowledge_ids` 批量摘掉 |
| `kb.created` | 知识库创建成功（**跳过** `is_temporary` 临时库） | 建库节点 |
| `kb.deleted` | 知识库软删成功（清理任务已入队） | **整库不可用**：按 `knowledge_base_id` 丢掉该库及库内全部知识。**P0 只投拥有空间** |
| `rbac.member_added` | 空间成员行创建成功 | 给该用户开通本空间知识权限 |
| `rbac.member_removed` | 成员被移除（含踢出；自愿离开用同一 type，用 `data.reason` 区分） | 收回该用户对本空间全部知识的访问 |
| `webhook.test` | 设置页点「测试」 | 验通，不改业务数据 |

**P0 投递范围：** 只查 **资源所属工作空间** 的端点。不扇出到组织成员。包络 `tenant_id` = 知识/库行上的 `tenant_id`。票内 `tenant_id` 与之一致，不存在跨空间 401。

删库 **禁止** 再发 N 条 `knowledge.deleted`（用一条 `kb.deleted`）。`kb.share_*` 见 §3.3（P1）。

### 3.2 知识库删除 / 移除：库内知识对本空间是否还可用？

**结论：不可用。接收方必须以库为粒度收口，不要等逐条 `knowledge.deleted`。**

| 动作 | 现网行为 | Webhook（P0 / P1） | 库内知识对本空间 |
|------|----------|---------|------------------|
| 删除本空间拥有的库 | `DeleteKnowledgeBase`：KB 行立刻软删；再清 share；`ProcessKBDelete` 走 **仓储**删文档 | **P0**：只向拥有空间发一条 `kb.deleted`。**禁止** `knowledge.deleted`。通知组织成员是 **P1** | **立即不可用**。文件随后物理清理 |
| 取消组织共享 / 入组 / 退组 / 删组织 | 见 §3.2.1 | **P1**（`kb.share_*`） | 对该成员空间不可用（源空间文件可能仍在） |
| 用户加入/移出**工作空间** | `tenant_members`：`AddMember` / Remove / Leave | **P0** `rbac.member_added` / `rbac.member_removed` | 空间和库都还在；**该用户**不能再访问本空间任何知识 |

约束：

1. `kb.deleted` **禁止**再扇出库内每一条 `knowledge.deleted`。payload 带 `cascade_knowledge: true` 与 `knowledge_count`。`ProcessKBDelete` 必须继续走仓储，不得改成 `knowledgeService.DeleteKnowledgeList`。
2. 接收方处理 `kb.deleted` 时：本地凡 `knowledge_base_id` 匹配的记录全部删除或标不可用。
3. `kb.deleted` 发出时源文件可能尚未清理完；对接方不要再去 download。此事件 **没有** `data.download`。

### 3.2.1 两层成员（**P1 备忘，本 PR 整节不接线**）

现网「共享空间」= **组织**。P0 **只**做 `tenant_members` 上的 `rbac.member_*`，**不**发 `kb.share_*`。下表留给 P1，避免以后把两层成员发错事件。实现 P0 时跳过本节余下发射点。

| 层 | 表 | 成员是 | 加入/退出现网入口 | webhook | 不该发 |
|----|-----|--------|-------------------|------------|--------|
| 工作空间成员 | `tenant_members` | **用户** ∈ 空间 | `AddMember`（含邀请接受）、`RemoveMember`、`POST /tenants/:id/leave` | **P0** `rbac.member_added` / `rbac.member_removed` | 不要当成「看见了共享库」 |
| 共享空间（组织）成员 | `organization_tenant_members` | **空间** ∈ 组织 | 见下行发射点 | **P1** `kb.share_added` / `kb.share_removed` | **不要**发 `rbac.member_*`。不要发明 `org.member_*`（P1 花名册另开） |

原因：

- 只在 `ShareKnowledgeBase` / `RemoveShare` 时按「当时的组织成员」扇出，**漏掉后加入的空间**：他们入组时库已经 share 过了，收不到 `share_added`，目录是空的。
- 空间退出组织时若不补 `share_removed`，对接方会一直以为这些库还在。
- 组织花名册（哪些空间在组织里）P1 再加 `org.member_added` / `org.member_removed`（`reason=removed|left`）。知识目录同步 **不需要** 这条也能做对。
- 审计里离开是独立的 `rbac.member_left`；webhook 仍合并为 `rbac.member_removed` + `data.reason=left`，避免接收方多一个分支。
- Agent 分享同一套组织成员模型，P0 知识回调 **不**发 Agent 事件。
- slj 另有 `knowledge_base_members`（库内用户角色），**不是**上游组织共享模型；本贡献 **不**为 kb_members 单独发事件。

发射点（组织层，**新插入成员行成功之后**，不要只 hook 其中一个 service 方法）：

- 私有 helper `emitSharesForNewOrgMember`：`ListByOrganization(orgID)` → 只向 **该 tenant_id** 发 `kb.share_added`。
- 调用方（insert 成功后）：`AddTenantMember`、`joinAsViewerWithChecks`（仅本次真正插入）、`ReviewJoinRequest` 的 **join** 审批通过分支。`CreateOrganization` 也可调（0 share → 0 事件）。
- **不要**在仓储 `orgRepo.AddTenantMember` 里 Emit。
- `joinAsViewerWithChecks` 已是成员提前返回时 **禁止** 调用 helper。
- `ReviewJoinRequest` 的 **upgrade** 分支只 `UpdateTenantMemberRole`，不发。
- `RemoveTenantMember` 成功 → 只向退出空间发 `kb.share_removed`（其它组织仍可见则跳过）。leave 与踢出都走这里，入口是对的。
- `DeleteOrganization`：删 share **之前**快照，按上表扇出 `share_removed`。
- 组织内 0 条 KB share：加入/退出 **不发** 知识事件。

`ShareKnowledgeBase` **新建行** 时仍向 **当时** 组织内每个成员空间 fan-out（跳过 `source_tenant_id`；不含「以后才加入」的）。已存在则只改权限，**不**发 `share_added`（权限变更是 P1 `kb.share_permission_changed`）。`RemoveShare` 须先列出成员再删行。以上全部 **P1 才实现**。

### 3.3 P1（本 PR 只登记名字，不实现发射）

| `type` | 说明 |
|--------|------|
| `kb.share_added` / `kb.share_removed` | 组织共享可见性；P0 **不发射** |
| `knowledge.updated` | 元数据 / 手工正文更新 |
| `knowledge.reparse_started` | 重解析入队 |
| `knowledge.parse_canceled` | 用户取消解析 |
| `kb.updated` | 库名/设置变更 |
| `kb.share_permission_changed` | 对已有组织 share 改权限（现网 `ShareKnowledgeBase` 走 Update） |
| `rbac.member_role_changed` | 工作空间内用户升降级 |
| `org.member_added` / `org.member_removed` | 空间加入/退出组织的花名册。P1 用 `kb.share_*` 表达库可见性即可，本 PR 不实现花名册事件 |
| `datasource.sync_completed` | 数据源一轮同步结束的汇总（P0 仍逐条 created） |

### 3.4 明确不发

- 问答 / Agent / 检索过程（已有 SSE EventBus）
- chunk / embedding 进度、`finalizing` 中间态
- Embed / IM 聊天事件（渠道 webhook）
- 删除知识库时的逐条文档删除
- **`knowledge_bases.is_temporary = true` 的临时库**及其上的知识（会话附件、内部隐藏库）
- 会话 `TemporaryDocument` / `TypeTemporaryDocumentProcess`（不走空间知识表的完成路径）
- **`EnsureOwner`**（注册 / CAS / 建空间引导，幂等且很吵）。成员事件只在 `AddMember` **新插入行**、Remove、Leave 时发
- 组织加入/退出时 **不**发 `rbac.member_*`；P0 **不**发独立的 `org.member_*`（见 §3.2.1）
- 组织加入/退出时不把同一条 `kb.share_*` 再广播给组织里其它空间
- Agent 组织分享、`knowledge_base_members` 库内用户成员
- 评测、clone 目标库创建过程中的内部过渡对象（若实现时无法区分，至少跳过 temporary）

## 4. 载荷契约（便于解析）

### 4.1 解析原则

1. **包络字段集合固定**，所有事件都有相同的顶层 key；没有的值用 `""` / `0` / `false` / `null`，**不缺 key**。
2. **唯一分支键**是顶层 `type`（字符串精确匹配）。不要用 URL path、不要用 `data` 里有没有某字段来猜类型。
3. **`data.resource` 标明资源种类**：`knowledge` | `knowledge_base` | `member` | `webhook`。同一 `resource` 下 `data` 的 key 集合固定。
4. **知识类事件**（created / parse_completed / parse_failed / deleted / batch_deleted）共用同一张 `data` 表，只用字段取值区分状态。
5. **禁止**把文件二进制、切片正文、向量、空间 API Key 放进 webhook。文件源只用 `data.download.ticket` 调 **`GET /api/v1/files/knowledge-download/:id`**。
6. 只增字段、不改已有字段类型。`spec_version` 现在恒为 `"1"`。
7. 知识类型字段叫 **`knowledge_type`**（取值对齐 REST 的 `type`：`file` / `url` / `manual` / `faq`），避免和包络顶层 `type`（事件名）撞名。

### 4.2 固定包络

| 字段 | 类型 | 始终存在 | 含义 |
|------|------|----------|------|
| `spec_version` | string | 是 | 协议版本，P0 为 `"1"` |
| `id` | string | 是 | 事件 ID（ULID/UUIDv7）。重试不变，**接收方去重键** |
| `type` | string | 是 | 见事件目录 |
| `time` | string | 是 | RFC3339 UTC |
| `tenant_id` | number | 是 | **资源所属工作空间**（投递查该空间的端点）。P0 不扇出，故与知识/库行 `tenant_id`、票内 `tenant_id` 相同。不是调用者 JWT 的 home tenant |
| `actor_user_id` | string | 是 | 操作者；系统任务为空串 |
| `request_id` | string | 是 | 追踪用，可空串 |
| `data` | object | 是 | 见各 `resource` 表 |

### 4.3 `data` 当 `resource=knowledge`

| 字段 | 类型 | 含义 |
|------|------|------|
| `resource` | string | 恒为 `"knowledge"` |
| `knowledge_id` | string | 文档 UUID；`batch_deleted` 时固定 `""` |
| `knowledge_base_id` | string | 所属库 UUID |
| `owner_tenant_id` | number | 库归属空间。P0 与包络 `tenant_id` 相同；P1 扇出时才可能不同 |
| `title` | string | 标题 / 文件名 |
| `knowledge_type` | string | 对齐 REST `type`：`file` / `url` / `manual` / `faq` |
| `source` | string | URL 源的原始地址；文件/手工可为空串 |
| `file_type` | string | 扩展名，如 `pdf`；非文件为空串 |
| `parse_status` | string | `pending` / `processing` / `completed` / `failed` / `cancelled` / `deleting` |
| `enable_status` | string | `enabled` / `disabled`。流水线快照：**不是**用户开关。入库与重解析中为 `disabled`；`parse_completed` 时为 `enabled` |
| `folder_path` | string | 库内目录，与 `NormalizeKnowledgeFolderPath` 一致：**根目录是空串 `""`**，无前导 `/` |
| `error_message` | string | 失败原因；成功时 `""` |
| `deleted` | bool | `knowledge.deleted` / `batch_deleted` 为 `true`；其余知识事件为 `false`（与示例一致，不缺 key） |
| `knowledge_ids` | string[] | 单条事件为 `[]`；仅 `batch_deleted` 填 ID 列表（最多 100，超出截断） |
| `count` | number | 单条为 `0`；批量时为实际删除总数 |
| `truncated` | bool | 单条为 `false`；批量且 `count > len(knowledge_ids)` 时为 true。为 true 时按 §2.3 **对账该库仍存在的文档**，不要指望列表返回已删 id |
| `download` | object | 见 §5，结构固定 |

### 4.4 `data` 当 `resource=knowledge_base`

| 字段 | 类型 | 含义 |
|------|------|------|
| `resource` | string | 恒为 `"knowledge_base"` |
| `knowledge_base_id` | string | 库 UUID |
| `name` | string | 库名 |
| `visibility` | string | 仅 `private` / `shared`（现网 `KnowledgeBaseVisibility` **没有** `public`） |
| `cascade_knowledge` | bool | `kb.deleted` 时为 `true`：库内知识全部对本空间不可用 |
| `knowledge_count` | number | 删除瞬间库内文档数（尽力而为，可 0） |
| `unavailable_to_tenant` | bool | `true` 表示本空间不能再访问该库（删除或取消共享） |
| `share_id` | string | 仅 share 事件；否则 `""` |
| `source_tenant_id` | number | 仅 share 事件：库归属空间；否则 `0` |

| 字段 | 类型 | 含义 |
|------|------|------|
| `resource` | string | 恒为 `"member"` |
| `user_id` | string | 被操作用户 |
| `role` | string | `owner` / `admin` / `contributor` / `viewer` |
| `reason` | string | `added` / `removed` / `left`（自愿离开） |
| `email` | string | 有则填，无则 `""`（不保证有，解析时当可选展示） |

### 4.6 `data` 当 `resource=webhook`

| 字段 | 类型 | 含义 |
|------|------|------|
| `resource` | string | 恒为 `"webhook"` |
| `ok` | bool | 恒为 `true`（测试事件无业务副作用） |

### 4.7 接收方状态机（P0，乱序合法）

`created` 在 HTTP 进程入 outbox，`parse_completed` 在 worker 入 outbox，两条 `webhook:deliver` **独立**，**completed 可以先到**。P0 不保证同一 `knowledge_id` 有序（有序是 P2）。

对端按 `knowledge_id`（`batch_deleted` 则按 `knowledge_ids[]`）维护本地行：

| 到达的 `type` | 本地还没有该 id | 本地已有该 id |
|---------------|-----------------|---------------|
| `knowledge.created` | upsert 占位：`parse_status=pending`（以 payload 为准），可按票拉文件 | **不得**把已是 `completed` 的行打回 `pending`。只补缺失字段（标题、票） |
| 同 `knowledge_id` 的 `deleted` 与 `created`（`moveKnowledgeReparse` 换库） | 按到达顺序：deleted → 墓碑；随后 created → 按 **新** `knowledge_base_id` upsert | created 先到 → 迁到新库；随后 deleted **不得**删掉已在新库的行（用 payload 的 `knowledge_base_id` 判断：deleted 带旧库 id 则只清旧库视图） |
| `knowledge.parse_completed` | upsert 为可检索（看 `enable_status`） | 更新状态；可再拉详情 |
| `knowledge.parse_failed` | upsert 为失败 | 标失败 |
| `knowledge.deleted` | 忽略或记墓碑 | 删除本地行 |
| `knowledge.batch_deleted` | 对列表中每个 id 同 deleted；`truncated` 则按 §2.3 对账仍存在的文档 | 同上 |
| `kb.deleted` | 按 `knowledge_base_id` 清空本地该库全部知识 | 同左 |

去重键永远是包络 `id`，不是 `knowledge_id`。同一文档重解析会再来一条新 `id` 的 `parse_completed`。

## 5. 知识创建与下载

Webhook **不传文件二进制**。文件型事件在 `data.download` 里只给 **一种** 取文件方式：5 分钟、只绑这一份知识的下载票 + 票面路径。JWT / 空间 API Key **不出现在事件里**，也不作为回调契约的第二种下载方案（现网 Contributor 下载接口保持原样，与本模块无关）。

### 5.1 `data.download` 固定结构

| 字段 | 类型 | 含义 |
|------|------|------|
| `available` | bool | 现在能否用票面 path 拉到源文件 |
| `reason` | string | `available=false` 时的原因，见下表；可用时为 `""` |
| `http_method` | string | 恒为 `"GET"` |
| `path` | string | `/api/v1/files/knowledge-download/{id}`；不可用时 `""` |
| `ticket` | string | 下载票；未签发时 `""` |
| `ticket_expires_at` | string | 票过期时间 RFC3339 UTC；未签发时 `""` |
| `ticket_header` | string | 恒为 `"X-WeKnora-Download-Ticket"` |

接收方用法：`GET {WEKNORA_BASE}{path}`，Header `{ticket_header}: {ticket}`。没有第二种 Header。不设 `auth_modes`：票面路径只认这一张票，列 `bearer` / `api_key` 会让对端误以为 `path` 还能用 JWT 或空间 Key。

**何时 `available=true`：** 有源文件且已配 `SYSTEM_AES_KEY`。未配密钥、非文件、已删：`available=false`，`ticket=""`，`path=""`。

`reason` 枚举（便于 switch）：

| `reason` | 何时 |
|----------|------|
| `""` | 可下载 |
| `not_a_file` | `knowledge_type` 为 `url` / `manual` / `faq`，没有源文件 |
| `no_file` | 类型是 file 但尚未落存储（理论上 created 之后不应出现） |
| `deleted` | 文档已删 |
| `kb_deleted` | 整库已删，不要再 download |

### 5.2 下载票（P0）

能力票据，对标 `GET /api/v1/files/presigned` 的 HMAC（`internal/utils/presign.go`），绑定 **knowledge_id** 而不是存储路径。**不是** 空间 `X-API-Key`。

| 项 | 约定 |
|----|------|
| 有效期 | 默认 **5 分钟**（`WEBHOOK_DOWNLOAD_TICKET_TTL`，上限 15 分钟） |
| 范围 | 只能 `GET` 票面里那一个 `knowledge_id` 的源文件 |
| 次数 | 有效期内允许多次 GET（下载重试）；不是单次作废 |
| 不能做 | 不能当空间 Key；不能检索、列表、删除、预览其它文档 |
| 何时签发 | DeliverWorker **每次出站 POST 前现签** |
| 何时不签发 | 非 file、已删、整库已删、未配置 `SYSTEM_AES_KEY` |

入队只存领域事件（无 ticket）。Webhook 重试可能到数分钟后才送到，冻在任务里的票会过期。worker 在 POST 前 mint，过期从 **本次 POST** 起算 5 分钟；`X-WeKnora-Signature` 按 **本次含新票的 body** 计算。

票格式（无状态，不写 Redis）：

```text
canonical = purpose=knowledge_download&knowledge_id=<uuid>&tenant_id=<n>&expires=<unix>
sig       = hex(HMAC-SHA256(SYSTEM_AES_KEY, canonical))
ticket    = wdt1.<base64url(canonical)>.<sig>
```

`tenant_id` = **知识行归属**（与 `data.owner_tenant_id` 相同）。与 presign 共用 `SystemHMACKey()`。`purpose` 防止拿文件 presign 的 sig 来下知识源文件。

校验走 **独立匿名面** `GET|HEAD /api/v1/files/knowledge-download/:id`（**不改**现网 `GET /api/v1/knowledge/:id/download` 的 Contributor+ / API Key `retrieve` 鉴权）：

1. 路由登记在 `noAuthAPI`，键为 **`/api/v1/files/knowledge-download*`**，methods **`GET, HEAD, POST`**（renew 是 POST；只写 GET 会让换票 401）。`Auth` 白名单只能精确路径或 `*` 前缀；不能把 `/api/v1/knowledge/` 加白名单，否则整个知识 API 免登。
2. Handler 读 Header `X-WeKnora-Download-Ticket`：HMAC 恒定时间比较 → 未过期（允许 30s 时钟偏差）→ `knowledge_id` 与 URL `:id` 一致 → 票内 `tenant_id` 与 **知识行 `TenantID`（归属）** 一致 → 文档未删且有源文件。
3. **只接受下载票**。带 JWT / API Key 但不带票 → 仍 401。现网 `GET /knowledge/:id/download` 不在本回调契约内，本模块不改、不在 payload 里指引。
4. 票无效、过期、id 不一致 → 401；知识已删或无文件 → 404。
5. 不复用 `GET /r/:token`：那是 DB grant，比无状态 HMAC 重，且绑定存储路径不是 knowledge_id。
6. 注册顺序对齐 `servePresignedFiles`：挂在 **Auth 之后** + `noAuthAPI` 放行。不要学 `serveResourceGrants`（`/r/:token` 在 Auth 之前登记），以免 `/api/v1/files/*` 绕过全局中间件顺序，后续难测。
7. 路由同时登记 GET 与 HEAD（对端探测 Content-Length），payload 里 `http_method` 仍固定 `"GET"`。Gin：**不要**给 `:id` 挂 POST（无路由 404）；只给 `:id/renew` 挂 POST。

**换票（延迟下载的正式办法）：**

```text
POST /api/v1/files/knowledge-download/:id/renew
Header: X-WeKnora-Download-Ticket: <旧票>
```

- 旧票必须绑这个 `:id`；**允许已过期**，但过期不超过 `WEBHOOK_DOWNLOAD_TICKET_RENEW_GRACE`（默认 **1 小时**，上限 24h）。
- 成功：200 `{ "ticket", "ticket_expires_at", "path", "ticket_header" }`，新票仍 5 分钟、仍只能下这一份文件。
- 超过宽限、purpose 不对、知识已删：401 / 404，必须再等一条带新票的 webhook（或对端改用自己的 Contributor 登录走现网 download，**不在**回调契约里）。
- 同样走 `noAuthAPI` 前缀；只认票，不认 JWT。
- 换票 **不**发 `webhook` 事件、不写投递表。

对接方：webhook handler 里不要同步下大文件；把 `id + ticket` 丢进自己的队列；worker 先 GET，若 401 再 `POST .../renew` 后重试 GET。

单测：过期、错 id、错 purpose、无密钥、无票、带 JWT 但不带票仍 401。过期 2 分钟的票 renew 成功；过期超过 grace 失败。票不写入 `tenant_webhook_deliveries`；应用日志脱敏。

泄露面：回调 URL 配错时，攻击者可用票下这一份源文件；票本身 5 分钟，但 **1 小时宽限内可换新票**，实际窗口按 renew grace 计。比泄露空间 API Key（可检索/可写）仍可接受。缓解：HTTPS、SSRF、短 TTL、范围绑定、**不向共享空间发票**。

### 5.3 接收方怎么下载（文件型）

`WEKNORA_BASE` 由对接方配置，不写进 webhook。

```bash
curl -OJ "$WEKNORA_BASE/api/v1/files/knowledge-download/<knowledge_id>" \
  -H "X-WeKnora-Download-Ticket: <data.download.ticket>"
```

收到 `knowledge.created` 且 `available=true` 后应尽快拉源文件。来不及可丢进自己的队列，票过期后走 §5.2 **换票**，不要隔夜超过 renew grace。目录保持处理中，等 `parse_completed` 再按 `enable_status` 开放检索。非文件不发票：`url` 用 `data.source`；`manual` / `faq` 事件不带正文。

### 5.4 各类型对照

| `knowledge_type` | created 时 `available` | `ticket` | 正文怎么拿 |
|------------------|------------------------|----------|------------|
| `file` | `true`（已配 `SYSTEM_AES_KEY`） | 有 | 票 + `path` |
| `url` | `false`，`reason=not_a_file` | `""` | `data.source` |
| `manual` / `faq` | `false`，`reason=not_a_file` | `""` | 本事件不提供；需要全文时走对接方已有的详情 API，不属于回调契约 |

## 7. HTTP 投递协议（对应原先的 Header 示例）

这段说的不是「你去调 WeKnora」，而是 **WeKnora 作为客户端，向你在设置里填的回调 URL 发 POST**。

### 7.1 一次投递长什么样

假设空间里配了：

- 回调 URL：`https://tg.example.com/hooks/weknora`
- 密钥：`whsec_test_secret_16`

用户上传成功后，WeKnora worker 对你的服务发出：

```http
POST /hooks/weknora HTTP/1.1
Host: tg.example.com
Content-Type: application/json
User-Agent: WeKnora-Workspace-Webhook/1.0
X-WeKnora-Event: knowledge.created
X-WeKnora-Delivery: dlv_01K3N8T9AAAA
X-WeKnora-Timestamp: 1756624860
X-WeKnora-Signature: sha256=3f1a...（见下）
Content-Length: 1234

{"spec_version":"1","id":"evt_01K3N8G2...","type":"knowledge.created",...}
```

你的 HTTP 服务要做三件事：**读 Header 路由 → 用原始 body 验签 → 解析 JSON 按 `type` 处理 → 尽快返回 2xx**。

### 7.2 请求头逐项

| Header | 谁用 | 说明 |
|--------|------|------|
| `Content-Type: application/json` | 解析器 | body 是 UTF-8 JSON |
| `User-Agent: WeKnora-Workspace-Webhook/1.0` | 日志 / 防火墙放行 | 与 Embed 的 `WeKnora-Embed-Webhook/1.0` 区分，两套出站不要混 |
| `X-WeKnora-Event` | **网关 / 路由** | 值等于 body 里的 `type`。可在 **不 parse body** 时把流量分到不同队列 |
| `X-WeKnora-Delivery` | 日志 | 本次投递 ID。asynq **同一任务重试时不变**（与表 `delivery_id` 对应）；重新入队才换新 id。业务去重用 body.`id`，不要用本 Header |
| `X-WeKnora-Timestamp` | 验签 / 防重放 | Unix 秒（投递时 `time.Now().Unix()`）。与 body 一起进 HMAC |
| `X-WeKnora-Signature` | 验真伪 | `sha256=` + hex(HMAC-SHA256(密钥, **`timestamp + "." + 原始 body 字节`**)) |

**与 Embed 不同：** Embed 只签 raw body。工作空间回调 **必须带 timestamp**。对端不要拿 Embed 示例代码直接套。5 分钟内重放仍可能，靠 body.`id` 去重。

### 7.3 怎么验签（必须用原始字节）

伪代码：

```text
ts = header["X-WeKnora-Timestamp"]
if ts missing or |now_unix - int(ts)| > 300:
    return 401   # 时钟差或重放窗口外
signed = ts + "." + raw_body_bytes   # 字符串拼接，中间一个点，不要 JSON
expected = "sha256=" + hex(HMAC_SHA256(secret, signed))
if not constant_time_equal(header["X-WeKnora-Signature"], expected):
    return 401
event = JSON.parse(raw_body_bytes)
```

注意：

- 先读 **原始 body** 再 `json.Unmarshal`。不要把对象再 `Marshal` 一遍去算 HMAC。
- 签名输入是 **ASCII 时间戳 + 一个点 + raw body**，点两边不要空格。
- 密钥是设置页里填的那串，**不会**出现在 Header 或 body 里。
- 未配置密钥时 P0 **不允许**创建端点（secret 最少 16 字符），避免裸 POST。

Python 示例：

```python
import hmac, hashlib, json, time
from flask import Flask, request

SECRET = b"whsec_test_secret_16"
app = Flask(__name__)

@app.post("/hooks/weknora")
def hook():
    raw = request.get_data()  # 原始字节
    sent = request.headers.get("X-WeKnora-Signature", "")
    ts = request.headers.get("X-WeKnora-Timestamp", "")
    if not ts.isdigit() or abs(int(time.time()) - int(ts)) > 300:
        return ("stale timestamp", 401)
    digest = hmac.new(SECRET, (ts + ".").encode() + raw, hashlib.sha256).hexdigest()
    expected = "sha256=" + digest
    if not hmac.compare_digest(sent, expected):
        return ("invalid signature", 401)
    event = json.loads(raw)
    # 也可先看 request.headers["X-WeKnora-Event"] 再决定是否入队
    if event["type"] == "knowledge.created":
        dl = event["data"]["download"]
        if dl.get("ticket"):
            # 立刻用票拉文件；不要在本 handler 里同步下大文件，丢进自己的队列
            # GET {WEKNORA_BASE}{dl["path"]}
            # Header: dl["ticket_header"] = dl["ticket"]
            pass
    return ("", 204)
```

### 7.4 接收方 HTTP 响应

| 你的状态码 | WeKnora 行为 |
|------------|----------------|
| 2xx | 成功，不再重试这条 delivery |
| 408 / 429 / 5xx | asynq 指数退避重试（最多 5 次，约 15s → 5min） |
| 其它 4xx（含 401 验签失败） | 视为配置错误，有限次后标记 failed，避免打爆 |

响应 **body 忽略**。请在 **10 秒内** 返回；落库、下载文件放到你自己的队列，不要在 webhook handler 里同步 `curl` 大文件。

### 7.5 和「下载知识」不是同一次 HTTP

容易混在一起的两段流量：

```text
① WeKnora ──POST JSON──► 你的 /hooks/weknora     （本节，事件通知）
② 你的后端 ──GET 文件──► WeKnora /api/v1/files/knowledge-download/:id  （§5，只用下载票）
```

① 认证靠回调 HMAC；② 认证靠 `X-WeKnora-Download-Ticket`（票在 ① 的 JSON 里，5 分钟有效）。方向相反，凭证不同。回调契约里没有 JWT / API Key 下载。

## 8. 数据模型

P0 **三张表**，都要进 PostgreSQL versioned migration 与 SQLite 镜像。现网最新 PG 编号是 `000079_knowledge_folder_path`，本模块用 **`000080_tenant_webhooks`**；SQLite 镜像用 **`000003_tenant_webhooks`**（现网 sqlite 最新是 `000002_knowledge_folder_path`）。合入前若上游又加了 migration，顺延编号，不要插队。

| 表 | 职责 | 生命周期 |
|----|------|----------|
| `tenant_webhook_outbox` | 领域事件持久化（at-least-once 的真源） | 物理行；`processed` 后保留 7 天再裁 |
| `tenant_webhook_endpoints` | 空间回调配置（URL、密钥、订阅事件） | 软删；每空间最多 5 条未删除行 |
| `tenant_webhook_deliveries` | 每次出站 POST 的排障记录 | 物理行；每个端点只保留最近 50 条 |

投递表**没有省略**，是 P0。它不是消息队列（队列在 asynq），只给人看最近成败：设置页列表、对端 4xx/超时排查。不存完整 JSON body，避免密钥/业务数据进排障表。

约束（应用层校验，不靠 DB CHECK，便于错误信息）：

- 每空间未删除端点 ≤ 5。
- `url` 生产必须 `https`；本地允许 `http://127.0.0.1` / `localhost`；写入前 `ValidateURLForSSRF`。
- `events` 必须是非空数组，元素必须是**当时已登记**的 `type`。禁止 `[]` 或省略：空数组若表示「全部 P0」，以后加事件会让旧端点突然收到新 type（隐性破坏）。UI 创建时默认勾选当时的 P0 列表并写入；未写入的未来 type 不投递。
- 明文 secret ≥ 16 字符；落库只存 AES-GCM 密文 `secret_enc`；API 只回 `has_secret`。

不建到 `endpoints.id` 的 FOREIGN KEY：端点软删后仍要能查历史投递；裁剪按 `endpoint_id` 等值删除即可。

### 8.1 `tenant_webhook_endpoints`

下列 `CREATE TABLE` 里的 `COMMENT '...'` **只作列意说明，禁止原样提交到 PostgreSQL migration**。现网 versioned 是 PG：落地 `000080` 必须把每条改成 `COMMENT ON COLUMN tenant_webhook_endpoints.<col> IS '...'`，表注释改成 `COMMENT ON TABLE ... IS '...'`。不要写 MySQL 列级 `COMMENT` 子句。

```sql
CREATE TABLE IF NOT EXISTS tenant_webhook_endpoints (
    id           VARCHAR(36) PRIMARY KEY COMMENT '端点 UUID，应用生成，36 字符',
    tenant_id    BIGINT NOT NULL COMMENT '所属工作空间 tenants.id；只向该空间端点投递',
    name         VARCHAR(64) NOT NULL DEFAULT '' COMMENT '设置页展示名，如「业务同步」；不参与 HTTP 投递',
    url          VARCHAR(512) NOT NULL COMMENT '回调地址。生产仅 https；本地允许 loopback http；写入与每次 POST 前 SSRF 校验',
    secret_enc   TEXT NOT NULL DEFAULT '' COMMENT 'HMAC-SHA256 密钥，AES-GCM 落库（同租户凭证助手）；API 永不回显',
    events       JSONB NOT NULL DEFAULT '[]'::JSONB COMMENT '订阅的 type 数组。禁止空数组（API 拒绝）；未订阅的未来 type 不投递',
    enabled      BOOLEAN NOT NULL DEFAULT TRUE COMMENT 'false 时跳过投递，不删配置、不删投递历史',
    description  VARCHAR(256) NOT NULL DEFAULT '' COMMENT '可选备注',
    created_by   VARCHAR(36) NOT NULL DEFAULT '' COMMENT '创建人 user id；系统/种子行为空串',
    created_at   TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '行创建时间 UTC',
    updated_at   TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '配置变更时间 UTC；投递尝试不更新此列',
    deleted_at   TIMESTAMP WITH TIME ZONE COMMENT '软删时间。NULL = 有效。未删除行上 (tenant_id, url) 唯一'
) COMMENT '工作空间出站回调端点。一行 = 一个 HTTPS 接收地址';

-- 设置页列表、Dispatch 时加载某空间全部未删除端点。
CREATE INDEX IF NOT EXISTS idx_webhook_ep_tenant
    ON tenant_webhook_endpoints (tenant_id)
    WHERE deleted_at IS NULL;

-- 同一空间不能重复填同一个 URL（仅未删除行）。
CREATE UNIQUE INDEX IF NOT EXISTS idx_webhook_ep_tenant_url
    ON tenant_webhook_endpoints (tenant_id, url)
    WHERE deleted_at IS NULL;
```

### 8.2 `tenant_webhook_deliveries`

每次 asynq `webhook:deliver` **终态**写一行（成功、耗尽重试失败、或判定为配置错误停止）。重试过程中的中间失败只更新将要插入的那一行的 `attempts` / `error`（同一 `delivery_id` upsert），避免一次事件把表打满。列注释落地规则同 §8.1。

```sql
CREATE TABLE IF NOT EXISTS tenant_webhook_deliveries (
    id            BIGSERIAL PRIMARY KEY COMMENT '自增游标；设置页按 id 倒序取最近投递',
    delivery_id   VARCHAR(64) NOT NULL COMMENT '本次投递 ID，对应 Header X-WeKnora-Delivery；入队时生成，asynq 重试（含 in-flight 推迟）不变',
    endpoint_id   VARCHAR(36) NOT NULL COMMENT '入队时的 tenant_webhook_endpoints.id；端点软删后历史仍可读',
    tenant_id     BIGINT NOT NULL COMMENT '空间 id 冗余，便于裁剪与按空间排查，无需 join',
    event_id      VARCHAR(64) NOT NULL COMMENT '领域事件 id（JSON 去重键 id）',
    event_type    VARCHAR(64) NOT NULL COMMENT '事件 type，与 JSON type、Header X-WeKnora-Event 相同',
    status        VARCHAR(16) NOT NULL COMMENT 'pending=在途或重试中；success=对端 2xx；failed=重试耗尽或不可重试 4xx',
    http_status   INTEGER NOT NULL DEFAULT 0 COMMENT '对端末次 HTTP 状态；超时/DNS/连不上为 0',
    attempts      INTEGER NOT NULL DEFAULT 0 COMMENT '该 delivery_id 已 POST 次数（asynq 重试，首次成功后为 1）',
    error         VARCHAR(512) NOT NULL DEFAULT '' COMMENT '末次错误或非 2xx 摘要，最多 512；成功为空串',
    duration_ms   INTEGER NOT NULL DEFAULT 0 COMMENT '末次 POST 往返毫秒',
    created_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '该 delivery_id 首次写入（入队/首次尝试）',
    finished_at   TIMESTAMP WITH TIME ZONE COMMENT '进入 success/failed 的时间；pending 时为 NULL'
) COMMENT '出站投递排障记录。不是队列：asynq 才是队列。不存事件 JSON body';


-- 设置页：某端点最近投递，按 id 倒序。
CREATE INDEX IF NOT EXISTS idx_webhook_dlv_endpoint_id
    ON tenant_webhook_deliveries (endpoint_id, id DESC);

-- 裁剪与按空间排查：DELETE ... WHERE tenant_id=? AND created_at < cutoff
-- 以及「该空间最近失败」。
CREATE INDEX IF NOT EXISTS idx_webhook_dlv_tenant_created
    ON tenant_webhook_deliveries (tenant_id, created_at);

-- 同一投递尝试幂等写入（asynq 重试更新同一 delivery_id）。
CREATE UNIQUE INDEX IF NOT EXISTS idx_webhook_dlv_delivery_id
    ON tenant_webhook_deliveries (delivery_id);

-- 每个（事件 × 端点）只认领一行，防止 outbox sweep 在 TaskID 释放后再入队双投。
CREATE UNIQUE INDEX IF NOT EXISTS idx_webhook_dlv_event_endpoint
    ON tenant_webhook_deliveries (event_id, endpoint_id);

-- 按事件反查「这个 evt_ 推了几次、到了哪些端点」。
CREATE INDEX IF NOT EXISTS idx_webhook_dlv_event_id
    ON tenant_webhook_deliveries (event_id);
```

`status` 取值：

| 值 | 含义 |
|----|------|
| `pending` | 已入队或正在重试，尚未拿到 2xx |
| `success` | 对端 2xx |
| `failed` | 重试耗尽，或 4xx（除 408/429）视为配置错误后停止 |

裁剪（`TypeWebhookDeliveryPrune`，走 `QueueWebhook`，**不要**挂 `QueueMaintenance`）：

```sql
-- 每个 endpoint 只留 id 最大的 50 行（即最近 50 次投递）。
DELETE FROM tenant_webhook_deliveries d
WHERE d.id NOT IN (
    SELECT id FROM tenant_webhook_deliveries
    WHERE endpoint_id = d.endpoint_id
    ORDER BY id DESC
    LIMIT 50
);
```

实现时按 `endpoint_id` 分组执行，避免一条 SQL 全表自关联。也可额外 `DELETE WHERE created_at < now() - interval '30 days'` 做时间兜底。

### 8.3 `tenant_webhook_outbox`

**没有这张表就不能声称 at-least-once。** 一行 = 一条领域事件（尚未按端点展开）。payload 是 **不含 download.ticket** 的 canonical JSON。P0 包络 `tenant_id` 即归属空间，Dispatch **不改写**。

```sql
CREATE TABLE IF NOT EXISTS tenant_webhook_outbox (
    id           BIGSERIAL PRIMARY KEY,
    event_id     VARCHAR(64) NOT NULL,
    event_type   VARCHAR(64) NOT NULL,
    owner_tenant_id BIGINT NOT NULL,
    payload      JSONB NOT NULL,
    status       VARCHAR(16) NOT NULL DEFAULT 'pending',
    attempts     INTEGER NOT NULL DEFAULT 0,
    last_error   VARCHAR(512) NOT NULL DEFAULT '',
    created_at   TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    processed_at TIMESTAMP WITH TIME ZONE
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_webhook_outbox_event_id ON tenant_webhook_outbox (event_id);
CREATE INDEX IF NOT EXISTS idx_webhook_outbox_status_created
    ON tenant_webhook_outbox (status, created_at)
    WHERE status = 'pending';
```

| `status` | 含义 |
|----------|------|
| `pending` | 已落库，尚未把所有端点任务交给 asynq |
| `processed` | 该扫到的（空间×端点）都已 `asynq.Enqueue` 成功（不是对端 2xx） |
| `failed` | 连续扫表超过上限（默认 50 次）仍无法入队，需人工；**不是**丢弃 payload |

流程：

1. 业务写成功 → `INSERT outbox`（应用内重试 3 次）。**这是唯一允许丢事件的窗口**（数据库不可写）。失败打 `webhook_outbox_insert_failed` 指标 + Error 日志，含 knowledge_id。
2. 同进程立刻 Dispatch 一次；失败保持 `pending`。
3. `webhook:outbox-sweep`（独立 webhook 队列，每 10s）捞 `pending`，过滤归属空间端点、认领 deliveries、入队 asynq，成功则 `processed`。
4. 已 `processed` 且 `processed_at < now()-7d` 由 prune 删除。

`Emit` **不是**「只打日志」。`Emit` = 写 outbox；写失败要让调用方可观测，但 **仍然不回滚** 已经成功的知识行（避免上传因 webhook 失败而 500）。

### 8.4 SQLite 对照

现网 sqlite 镜像没有 `JSONB` / `BIGSERIAL` / 部分索引。迁移时：

| PostgreSQL | SQLite |
|------------|--------|
| `JSONB` | `TEXT`，应用层 JSON 数组字符串 |
| `BOOLEAN` | `INTEGER` 0/1，或 SQLite 接受的 `BOOLEAN` |
| `TIMESTAMP WITH TIME ZONE` | `DATETIME` |
| `BIGSERIAL` | `INTEGER PRIMARY KEY AUTOINCREMENT` |
| 列/表 `COMMENT '...'` | sqlite 无 COMMENT，可改行内 `--` 或省略；PG 落地用 `COMMENT ON` |

不在 sqlite 上建 `WHERE deleted_at IS NULL` 的部分唯一索引时，用普通 `(tenant_id, url)` 并在应用层排除已删行。

### 10.1 发射点（EventSink，不包装整个仓储）

不要 Gin middleware，不要 GORM AfterUpdate，**不要** `type wrappingKnowledgeRepo struct { interfaces.KnowledgeRepository }`：该接口 30+ 方法，后续每次加方法都要转调，贡献 PR 维护成本不可接受。

做法：定义窄接口，注入到**已经会写库**的 service：

```go
type WorkspaceEventSink interface {
    Emit(ctx context.Context, ev WorkspaceEvent)
}
```

业务写成功后调用。`Emit` **只负责写 outbox**（重试 3 次）；展开端点与 asynq 由 Dispatcher / sweep 做。写 outbox 失败不回滚业务，但必须打指标。

**知识行插入成功 → `knowledge.created`（所属 KB `is_temporary=false`）。** 在 **`repo.CreateKnowledge` 返回 nil 之后** 调 Emit（不要只 hook 一个名叫 CreateKnowledge 的 service 方法，现网没有这一层）：

| 代码位置 | 场景 |
|----------|------|
| `CreateKnowledgeFromFile` | 上传文件；数据源带正文也走这里 |
| `CreateKnowledgeFromURL` / `createKnowledgeFromFileURL` | URL / 直链文件 |
| `CreateKnowledgeFromManual` | 手工 |
| `createKnowledgeFromPassageInternal` | Passage / PassageSync |
| `cloneKnowledge`（`knowledge_process.go`） | clone 复制一条；move 复制到目标库（新 UUID） |

**不发 created：** FAQ 容器行（`getOrCreateFAQKnowledge`、FAQ 一库一条的 type=faq 壳）。FAQ 条目是 chunk 不是知识行。

**知识行删除成功：**

| 代码位置 | 事件 |
|----------|------|
| `knowledgeService.DeleteKnowledge`（数据源替换、评测、会话、web_search、message） | `knowledge.deleted` |
| `knowledgeService.DeleteKnowledgeList` 且 `len==1` | `knowledge.deleted` |
| `knowledgeService.DeleteKnowledgeList` 且 `len>1` | **只** `knowledge.batch_deleted` |
| HTTP `enqueueKnowledgeListDelete` | **不发** |
| `ProcessKBDelete` → `kgRepo.DeleteKnowledgeList` | **不发**（已有 `kb.deleted`） |
| 临时库上的行 | 跳过 |

**同 ID 换库** `moveKnowledgeReparse`（只 Update `knowledge_base_id`）：对归属空间发 `knowledge.deleted`（旧库 id）再发 `knowledge.created`（新库 id），同一 `knowledge_id`。乱序见 §4.7。

**完成 / 失败**（先读旧 `parse_status`）：`FinalizeSubtask` 且 `promoted==true` → completed；`UpdateKnowledge` / `UpdateKnowledgeColumns` 非 completed→completed 含 clone 成功 defer；变为 failed → `parse_failed`；已经 completed 再改其它列 **不发**。

不要在 Repository 里 Emit。P0 只投 **归属空间** 端点。

**知识库 / 成员（服务层）：**

- **新插入** KB 行且 `!IsTemporary` → `kb.created`。入口至少：`CreateKnowledgeBase`、`DuplicateKnowledgeBase`、`CopyKnowledgeBase` 在 `dstKB==""` 时新建、`CreateSharedKnowledgeBase`。拷进**已有**目标库不发 `kb.created`
- `DeleteKnowledgeBase` 软删成功 → `kb.deleted` **只投拥有空间**。不通知组织成员（P1）
- `ShareKnowledgeBase` / `RemoveShare` / 入组 / 退组 / `DeleteOrganization`：**P0 不 Emit**
- `AddMember` **新插入成功** → `rbac.member_added`；Remove / Leave → `rbac.member_removed`
- **禁止**在 `EnsureOwner` 里 Emit
- 「测试」：指定 `hook_id` 发 `webhook.test`，绕过 `events` 过滤

完成事件只在 `RowsAffected>0` 或 `promoted==true` 时发。

### 10.2 asynq

新增独立池，**不要**挂 `QueueMaintenance`：

```text
WorkerPoolWebhook = "webhook"
QueueWebhook      = "webhook"          // Redis 物理名，禁止复用 "low"
TypeWebhookDeliver       = "webhook:deliver"
TypeWebhookOutboxSweep   = "webhook:outbox-sweep"
TypeWebhookDeliveryPrune = "webhook:delivery-prune"
```

三者都写入 `queueDefinitions`（Pool=`WorkerPoolWebhook`）。`internal/router/task.go` 增加 `webhookAsynqServer`，mux 只注册上述 type。container `Provide` 第 **7** 个 asynq Server（现网已有 core / postprocess / enrichment / maintenance / shared / wiki）。`WorkerPoolConcurrency` 增加 `Webhook` 字段（默认 4），对齐 wiki：**不要**并进 `DefaultUpstreamWorkerConcurrency`。`TestQueueDefinitionsAreUniqueAndConsumable` 的 `validPools` 必须加上 `WorkerPoolWebhook`，否则新队列会被判 unknown pool。`system_runtime_test` 同步加一档。

入队与投递细节见 **§2.2**。摘要：

- payload：`event_id` + `endpoint_id` + 归属 `tenant_id` + **入队时生成的 `delivery_id`**（无 ticket）
- `asynq.TaskID("wh:" + event_id + ":" + endpoint_id)`；`ErrTaskIDConflict` 视为已入队
- deliveries UNIQUE `(event_id, endpoint_id)` 做持久认领
- DeliverWorker：INCR 槽 → 满则 `return ErrWebhookInFlightBusy`（webhook Server：`IsFailure=false` + 3s 延迟）→ mint 票 → Timestamp HMAC → POST；`defer DECR`
- HTTP MaxRetry=5 只计真正的 POST 失败；4xx（除 408/429）才 SkipRetry
- Sweep / prune 走 `QueueWebhook`

## 12. 安全

1. SSRF：`ValidateURLForSSRF` + 安全客户端，重定向再校验。
2. HTTPS；仅 loopback 允许 http。内网放行靠 `WEBHOOK_ALLOW_PRIVATE_URLS`（默认 false）。
3. HMAC：**timestamp + "." + raw body**；密钥 AES 落库；不回显。与 Embed 只签 body 不同。
4. 端点 CRUD **Owner+** + `PathTenantMatch`；API Key 须声明 `manage_tenant_settings`。
5. 载荷无文件正文、无空间 API Key；文件事件含 5 分钟 `download.ticket`；过期后 1 小时内可换票。
6. in-flight 满了 **延迟再投、不丢**；`kb.deleted` 不扇出文档事件。
7. 端点 CRUD 写审计：`webhook.endpoint_created|updated|deleted`。
8. 下载票：HMAC 绑定 knowledge_id + **归属** tenant_id + exp + purpose；独立路由 + `noAuthAPI` 前缀（含 POST）；日志脱敏；不落投递表。
9. 票面路由 **不**挂 JWT 旁路到 `/knowledge/:id/download`。
10. 事件先写 outbox；没有 outbox 行不算已发出。
