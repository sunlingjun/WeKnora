# 2026-09-02 CAS 身份与 JWT 对齐

> **拍板**：CAS cookie 是 HttpOnly，前端不能拿 cookie 和 JWT 对比。每个整页刷新先 `GET /api/v1/cas/validate` 换发与当前 cookie 一致的 JWT；校验完成前不带本地 Bearer。后端在 JWT 的 `cas_user_id` 与 cookie uid 冲突时忽略该 JWT。没有 CAS cookie 不算冲突。

---

## 1. 要解决什么

换 CAS 账号后，浏览器 cookie 已是新用户，`localStorage` 里的 JWT 仍是旧用户。路由若发现本地有 JWT 就跳过 CAS，Auth 中间件又优先 Bearer，业务请求会按旧用户鉴权（权限串号）。

生产 `_cas_sid` / `_cas_uid`（测试环境 `_cas_t_sid` / `_cas_t_uid`）为 **HttpOnly**，`document.cookie` 读不到。把 cookie 绑到 localStorage 再对比，在生产是死代码。

## 2. 现行模型

### 前端（`*.nxin.com`）

| 规则 | 行为 |
| --- | --- |
| 每个整页刷新 | 必须先调 `GET /api/v1/cas/validate`（cookie 由浏览器自动带上） |
| 校验完成前 | 不附带本地 JWT / `X-Tenant-ID`（靠 cookie + 白名单 validate） |
| 校验成功 | `markCasIdentityReconciled()`，之后才允许带 JWT |
| 校验失败 | `logout()` 清残留 JWT，再跳 CAS 登录 |
| 同页 SPA 跳转 | 不再重复 validate；换账号后需刷新本页 |

关键文件：`frontend/src/utils/casSession.ts`、`frontend/src/stores/cas.ts`、`frontend/src/router/index.ts`、`frontend/src/utils/request.ts`。SSE（`api/chat/streame.ts`）与文件代理（`utils/protectedFileAccess.ts`）走同一套 `applyStoredAuthHeaders`。

### 后端

Auth 顺序（`internal/middleware/auth.go`）：

1. 免认证白名单 / OPTIONS（含 `GET /api/v1/cas/validate`）
2. Bearer JWT：有效且与 CAS uid cookie **不冲突** 则采纳
3. `X-API-Key`
4. 可选 `auth.nxin_cas_auth.enabled`：用 cookie 校验并绑定用户

冲突判定 `jwtIdentityConflictsWithCASCookie`：JWT 用户有 `cas_user_id`，请求上也有 CAS uid cookie，二者不一致 → **忽略 JWT**。无 cookie、或本地密码用户（空 `cas_user_id`）不算冲突。

## 3. 刻意不覆盖

同页不刷新、另一个标签换了 CAS：本页仍使用已 reconcile 的 JWT。安全靠后端忽略冲突 JWT，不靠前端读 cookie。

每次刷新会多一次 CAS validate 并换发新 JWT，这是 HttpOnly 下可落地的代价。

早期「把 `_cas_sid`/`_cas_uid` 写入 `weknora_cas_bound_*` 再对比」方案已删除。登出时 `clearStaleCasCookieBinding()` 只清旧 key，不再写入。
