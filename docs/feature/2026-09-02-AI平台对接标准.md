# 2026-09-02 WeKnora 对 AI 平台的对接标准

> **拍板**：对外说「我们是 **WeKnora**（腾讯开源企业级 RAG + 自研 Wiki）」。  
> 生成 Wiki 页面时按 **WeKnora Wiki 方言**，不要按 Obsidian / Docusaurus / Confluence 微调。  
> 可直接把 §0 整段转给对方 AI。

---

## 0. 给对方 AI 的标准答复（可复制）

```
平台：WeKnora（企业级 RAG + 自研 Wiki，不是 Obsidian / Docusaurus / Confluence）。

【写 Wiki 页面时】
- 链接语法：Obsidian 同款双括号，但目标是 slug 不是文件名。
  推荐：[[entity/acme-corp|Acme Corp]]
  也可：[[concept/rag]]
  禁止：相对路径（../foo.md）、Confluence 宏、裸 URL 当 wiki 链接。
- slug 格式：<page_type>/<name>，小写、连字符。
  page_type ∈ summary | entity | concept | index | synthesis | comparison
  例：entity/acme-corp、concept/rag、summary/<knowledge-uuid>
- 元数据不要写进 Markdown YAML frontmatter。title / summary / page_type / aliases / source_refs
  是独立结构化字段（REST / Agent 工具 / MCP），正文 content 只放 Markdown。
- aliases 是「同一事物的别名」数组（缩写、中英对照），不是标签，不是相关概念。
- 禁止自链接；禁止发明不存在的 slug；只链已有或本批次将创建的 slug。

【写 RAG 源文档（上传成知识）时】
- 普通 Markdown / PDF / Word / 网页即可，系统会切块+向量化。
- 不要依赖 YAML frontmatter：入库后会当噪声，展示时还会被剥掉。
- 业务字段走 custom_metadata JSON（≤20 键，值 string/number/boolean/null），或知识库标签。
- 手写 Markdown 知识：title + content，走 POST /knowledge-bases/{kb_id}/knowledge/manual。

【读知识时】
- MCP：tencent-weknora-mcp（约 30 个工具，含检索 / 问答 / Wiki 读）
- REST：X-API-Key + /api/v1
- 开放检索：POST /api/v1/open/knowledge/retrieve（专用 Key，无登录）
```

## 1. 我们是什么（先分清三套 Markdown）

本仓库里同时存在三套「看起来像 Wiki」的 Markdown，**对方 AI 要微调的是第 1 套**。

| # | 是什么 | 位置 / 产物 | 链接 | 元数据 |
|---|--------|-------------|------|--------|
| **1. 产品 Wiki（拍板对象）** | WeKnora 知识库里 LLM 生成、可浏览可给 Agent 当长期记忆的互联页面 | 运行时 `wiki_pages`；Agent 工具 `wiki_*`；MCP `wiki_search/read/index` | `[[slug\|title]]` | 结构化字段，**不是**正文 YAML |
| **2. 产品文档站** | 给人看的官方文档 | `website-docs/`，VitePress，`base: /docs/` | 相对路径 `[文](./foo.md)` | VitePress frontmatter（`title`/`layout`/`sidebar`） |
| **3. 仓库文档 wiki 镜像** | 给人/Agent 在 Git 里读的项目说明 | `docs/wiki/` | 相对路径 `(开启知识图谱功能.md)` | 类 Obsidian：`title` / `tags` / `aliases` |

第 2、3 套不要拿去「导入 WeKnora Wiki」。文档站继续 VitePress；Git wiki 继续相对链接。只有**往知识库 Wiki 里写页面**才用第 1 套。

WeKnora 本身还是 RAG 平台：文档入库 → 切块 → 向量/关键词检索 → 问答；Wiki 是索引策略开关（`indexing_strategy.wiki`），不是另一个产品。

## 2. WeKnora Wiki 方言（写入标准）

### 2.1 链接

解析见 `internal/application/service/wiki_page.go` 的 `wikiLinkRegex` / `parseOutLinks`。

```markdown
正确：
见 [[entity/acme-corp|Acme Corp]] 与 [[concept/rag]]。

错误：
见 [Acme](../entity/acme-corp.md)          ← VitePress / Docusaurus
见 [[Acme Corp.md]]                       ← Obsidian 文件名
见 <ac:link>...</ac:link>                 ← Confluence
```

- `[[slug|display]]`：slug 必须精确；display 给人看。
- `[[slug]]`：合法，但提示词要求提到已有条目时优先带 display。
- 代码块、行内 code、已有 `[[...]]`、`[text](url)`、图片 `![]()` 内不会再被自动 linkify。
- 重命名 slug 会改写全库反向链接；死链在 finalize / lint / `wiki_delete_page` 时清理。

### 2.2 页面字段（相当于「frontmatter」，但是 API 字段）

`WikiPage`（`internal/types/wiki_page.go`）与 `wiki_write_page` 工具对齐：

| 字段 | 必填 | 说明 |
|------|------|------|
| `slug` | 是 | KB 内唯一，`<type>/<name>` |
| `title` | 是 | 人类可读标题 |
| `summary` | 是 | 一行摘要，进索引列表 |
| `content` | 是 | **完整** Markdown 正文，不要占位符，不要 YAML 头 |
| `page_type` | 是 | `summary` / `entity` / `concept` / `index` / `synthesis` / `comparison` |
| `aliases` | 否 | 同指别名；传入则整表替换 |
| `source_refs` | 否 | `"<knowledge_id>\|<doc_title>"` 或短 `dN`；传入则整表替换 |

`synthesis` / `comparison` **只能**由 Agent `wiki_write_page` 创建，ingest 管道不会自动生成。

状态：`draft` / `published`（默认）/ `archived`。目录最多 3 级，ingest 规划通常 2 级。

### 2.3 不要写 YAML frontmatter 进 Wiki 正文

Wiki 元数据在数据库列里，不在 `content` 里。正文以 `---` 开头会被当成普通 Markdown，还可能和展示侧的 frontmatter 剥离逻辑打架。

对比：Agent Skill 的 `SKILL.md` **必须** YAML frontmatter（`name` + `description`），那是另一条链路，见 §4.5。

### 2.4 aliases 语义

只收录「同一事物」的别名：缩写、全称/简称、中英对译。  
不要把上级品类、相关产品、宽泛概念放进 aliases（ingest 提示词：`related ≠ same`）。

## 3. RAG 源文档方言（入库标准）

Wiki 是「整理后的条目」；RAG 知识是「原始资料」。两者不要混用同一套 frontmatter。

| 入口 | 内容形态 | 元数据怎么给 |
|------|----------|----------------|
| 文件上传 | PDF / Word / Excel / MD / EPUB 等 | 知识库标签；上传后 `custom_metadata` |
| URL 导入 | 网页正文 | 同上 |
| 手写 Markdown | `title` + `content` | `POST .../knowledge/manual`；`tag_ids`；之后 PATCH `custom_metadata` |
| MCP | `create_knowledge_from_file` / `_url` / `_text` | 与上相同 |
| Claw Skill | 上传 / URL / 写 MD / 检索 | 薄封装 REST |

`custom_metadata` 约束：≤20 字段；键 1–64 字符；值 string / number / boolean / null，≤1000 字符。会进摘要与模型上下文。

YAML frontmatter（`title`/`tags`/`aliases` 那种）**不是** WeKnora 知识元数据协议：切块展示时会被当成噪声剥掉。

## 4. 本项目可提供给各 AI 平台的标准（读/写能力）

按对方生态选一层即可，底层都是同一套 `/api/v1`。

### 4.1 MCP Server（优先给 Claude Desktop / Cursor / VS Code Copilot）

- 包：`tencent-weknora-mcp`（PyPI），入口 `weknora-mcp-server`
- 传输：stdio / SSE / Streamable HTTP
- 凭证：`WEKNORA_BASE_URL` + `WEKNORA_API_KEY`
- 能力（约 30 个工具）：空间、知识库、混合检索、文件/URL/文本入库、模型、会话、RAG `chat`、Agent `agent_chat`、分块、Wiki 读（`wiki_search` / `wiki_read_page` / `wiki_index_view`）
- Wiki **写**不在 MCP 里，在产品内 Agent 工具（`wiki_write_page` 等 10 个）

配置样例见 `mcp-server/MCP_CONFIG.md`。

### 4.2 REST API（任意 HTTP 客户端 / 自建 Agent）

- Base：`/api/v1`
- 认证：`X-API-Key` 或登录 Bearer；scoped API Key 可按能力 + 按库收窄
- 权威 schema：非 release 模式 ` /swagger/index.html`
- Wiki：`/api/v1/knowledgebase/:kb_id/wiki/...`（无免登录公开站）
- 知识检索：`POST /api/v1/knowledge-search`（登录/API Key，有权限）

### 4.3 开放检索（三方模型只拼上下文、不登录）

- `POST /api/v1/open/knowledge/retrieve`
- 头：`X-Open-Retrieve-Api-Key`（与用户 Key 分开）
- 入参：`query` + `knowledge_base_ids` 和/或 `knowledge_ids`
- 出参：chunk `content` + `score` + `match_type`
- 文档：`docs/api/open-knowledge-retrieve.md`

适合天工 / 学联网 / 其它只需要「检索片段」的 BFF，不适合当完整 Wiki 编辑协议。

### 4.4 Claw Skill（OpenClaw / ClawHub）

- 包：`@lyingbug/weknora`
- 能力：上传、URL、写 Markdown、hybrid-search / knowledge-search、浏览知识库
- 比 MCP 轻，不含 Wiki 读、不含 Agent 对话

### 4.5 Agent Skills（给 WeKnora 自己的智能体加说明书）

对方若在 **WeKnora 产品内**扩展 Agent，用 Anthropic 风格 `SKILL.md`：

```yaml
---
name: pdf-processing          # 1-50，汉字/字母/数字
description: ...触发条件...    # 1-500
---
```

这是 Skill 协议，不是 Wiki 协议。

### 4.6 CLI（脚本与 Agent 编排）

- 二进制 `weknora`：`kb` / `doc` / `search` / `chat` / `agent` / `mcp serve`
- Agent 友好：JSON envelope、`weknora schema`、`--dry-run`、类型化退出码
- 文档：`website-docs/05-clients/02-cli.md`

### 4.7 其它入口（不是 Markdown 方言，但是对接面）

| 入口 | 给谁 | 备注 |
|------|------|------|
| Go client SDK | 后端集成 | `github.com/Tencent/WeKnora/client` |
| 网页 Embed | 外站挂问答 | 匿名访客；图片不走 `resource_urls=public` |
| IM | 企微 / 飞书 / Slack / 钉钉等 | 对话渠道，不是文档导入协议 |
| 数据源连接器 | 飞书 Wiki/云盘、语雀、Notion、RSS | **从那些平台拉进 WeKnora**，方向相反 |

飞书/语雀/Notion 是 **ingest 来源**，不是我们对外输出的 Wiki 语法。不要让对方 AI 按飞书 wiki 语法写内容再期望 WeKnora Wiki 原样理解。

## 5. 对方 AI 该选哪套（决策表）

| 对方在干什么 | 用哪套标准 |
|--------------|------------|
| 生成/改 WeKnora 知识库 Wiki 页面 | **§0 + §2 WeKnora Wiki**（本拍板） |
| 生成将要 **上传进知识库** 的资料 | **§3 普通 Markdown**，元数据走 `custom_metadata` / 标签 |
| 改本仓库 `website-docs/` | VitePress：相对路径 + 其 frontmatter |
| 改本仓库 `docs/wiki/` | Git 文档：相对 `.md` + `title/tags/aliases` |
| 在 Cursor/Claude 里查我们的知识库 | MCP `tencent-weknora-mcp` |
| 在 OpenClaw 里存取资料 | Claw Skill |
| 三方模型只要检索片段 | 开放检索 API |
| 给 WeKnora Agent 加技能 | `SKILL.md` frontmatter |

---

## 6. 明确不做

- 不把 Obsidian `[[文件名]]`、Docusaurus 相对路径、Confluence 存储格式当作 Wiki 写入协议。
- 不把 YAML frontmatter 当成 Wiki 或 RAG 的一等元数据。
- 不为「让某个通用写作 AI 少转换」去改产品 Wiki 语法；产品已经按 `[[slug\|title]]` 写死在 ingest、lint、Agent 工具、前端编辑器里。
- 文档站（VitePress）与产品 Wiki 继续分轨，不互相迁就字段名。
